# AGENTS.md

# 晨光 Agent 平台 - AI Development Guidelines

## 1. 文档优先原则

在修改代码前，必须阅读：

1.  `PROJECT_CONTEXT.md`
2.  当前任务涉及模块的源码
3.  相关 API、数据模型和配置

`PROJECT_CONTEXT.md` 描述项目当前状态。 `AGENTS.md` 描述 AI
在本项目中的开发规则。

------------------------------------------------------------------------

# 2. 核心开发原则

## 2.1 理解后修改

禁止：

-   未阅读代码直接修改
-   根据文件名猜测业务逻辑
-   创建重复实现

修改前需要明确：

-   当前实现方式
-   修改影响范围
-   是否影响 API、数据库、前端调用

------------------------------------------------------------------------

## 2.2 最小修改原则

默认采用最小范围修改。

禁止：

-   无需求的大规模重构
-   删除已有功能
-   修改无关模块
-   引入没有必要的新依赖

如果发现架构问题：

先说明问题、风险和建议方案。

------------------------------------------------------------------------

# 3. 后端架构规范

项目后端采用分层架构：

    API Layer
        ↓
    Service Layer
        ↓
    Repository Layer
        ↓
    Database / Infrastructure

## API Layer

负责：

-   HTTP 路由
-   参数校验
-   Dependency 注入
-   Response 返回

禁止：

-   编写复杂业务逻辑
-   直接操作数据库

------------------------------------------------------------------------

## Service Layer

负责：

-   核心业务逻辑
-   多模块流程编排
-   事务控制
-   外部服务调用

------------------------------------------------------------------------

## Repository Layer

负责：

-   数据查询
-   ORM 操作
-   数据持久化

禁止：

-   编写业务规则
-   处理 HTTP 逻辑

------------------------------------------------------------------------

# 4. FastAPI 开发规范

必须：

-   使用异步接口
-   使用 Dependency Injection
-   使用 Pydantic Schema
-   明确 Request / Response Model

禁止：

直接返回 ORM 对象。

------------------------------------------------------------------------

# 5. SQLAlchemy 与数据库规范

使用 SQLAlchemy 2.0 风格。

推荐：

``` python
select(User)
```

禁止：

``` python
session.query(User)
```

数据库结构变化：

必须：

1.  修改 Model
2.  创建 Alembic Migration
3.  检查 Migration
4.  执行测试

禁止：

直接修改数据库结构。

------------------------------------------------------------------------

# 6. API 规范

业务接口统一返回：

``` json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

修改接口必须考虑：

-   前端兼容
-   数据结构变化
-   已有调用方

------------------------------------------------------------------------

# 7. 权限规范

项目采用：

    User
     ↓
    Role
     ↓
    Permission

所有需要保护的管理接口：

必须使用权限依赖。

禁止：

只通过前端隐藏按钮实现权限控制。

------------------------------------------------------------------------

# 8. Redis 使用规范

新增缓存必须明确：

-   Key 设计
-   Value 格式
-   TTL
-   失效策略

禁止：

无过期时间缓存。

------------------------------------------------------------------------

# 9. 前端开发规范

所有前端代码必须位于：

    app/

禁止：

前端代码放入后端目录。

------------------------------------------------------------------------

前端开发必须基于真实后端：

开发前确认：

-   API 地址
-   请求参数
-   返回结构
-   权限要求

禁止：

长期使用不存在于后端的 Mock 数据。

------------------------------------------------------------------------

# 10. AI 应用开发规范

涉及：

-   LLM
-   Agent
-   RAG
-   Tool Calling

必须明确：

## Agent

需要定义：

-   Role
-   Goal
-   Tools
-   Constraints
-   Memory

禁止：

无限权限 Agent。

------------------------------------------------------------------------

## Prompt

Prompt 不允许散落在业务代码。

应该：

-   独立管理
-   版本可追踪
-   便于评估

------------------------------------------------------------------------

## RAG

需要记录：

-   数据来源
-   文档版本
-   Metadata
-   Embedding 策略

------------------------------------------------------------------------

# 11. 代码风格

## 注释

代码注释统一使用中文。

重点说明：

-   为什么这样设计
-   特殊业务原因
-   注意事项

避免：

解释显而易见代码。

------------------------------------------------------------------------

## 类型

优先使用明确类型。

避免：

-   滥用 Any
-   隐式类型转换

------------------------------------------------------------------------

# 12. 测试要求

新增功能必须考虑：

-   正常流程
-   异常流程
-   边界情况

涉及权限：

必须验证：

-   普通用户
-   管理员
-   无权限用户

------------------------------------------------------------------------

# 13. Git 安全

修改前：

检查：

``` bash
git status
```

完成后：

检查：

``` bash
git diff
```

禁止：

-   覆盖用户未提交修改
-   删除未知文件
-   重置用户工作区

------------------------------------------------------------------------

# 14. AI 工作流程

执行开发任务时：

## Step 1

理解：

-   项目上下文
-   当前代码
-   数据流

## Step 2

分析：

-   修改方案
-   影响范围

## Step 3

实施修改。

## Step 4

验证：

-   测试
-   构建
-   类型检查

------------------------------------------------------------------------

必须说明：

## Changed

修改了哪些文件。

## Implementation

实现了什么。

## Verification

执行了哪些验证。

## Risk

剩余风险。
